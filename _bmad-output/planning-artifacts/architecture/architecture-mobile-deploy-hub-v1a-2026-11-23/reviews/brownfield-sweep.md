### Design risks
- withLock errors carry no .code (lock.mjs:94). hub-device report() maps only error.code HUB_LOCK_TIMEOUT to exit 76 (:251) and catchup matches message text. FR-30 'pending instead of red' needs a coded error (and keeping the legacy message prefix `host lock <name> is held` for catchup.mjs:469/:591 regexes and old pinned releases during the pin-flip window).
- Old-release coexistence: catch-up runs from the INSTALLED release while deploy jobs run from the pinned @v1 hub; an old lock.mjs treats a lease as a dead job when its pid is gone (leaseSupport comment hub-device.mjs:109-110, :115) and, more importantly, an old withLock (mkdir spin, ignores <name>.queue) will barge ahead of queued waiters. Queue-joining only holds when every contender runs the new code; mixed versions silently break FIFO and could starve queued deploy tickets (a ticket whose owner never takes the lock is only pruned if its pid dies, staleWaiter lock.mjs:139-146).
- staleWaiter (lock.mjs:139-146) requires ticket.host===hostname(), integer pid and process_start; GitHub runner job tickets from the Mac (mac-ios lock lives on the Mac's disk per CLAUDE.md) or any other host are always judged stale and pruned by the first acquireLease poll on a different host. Job tickets for mac-ios/remote runners need a different liveness rule, and the frozen ticket format must carry host-specific liveness. Also ticket filename embeds only pid for ordering (:201), so cross-host ordering relies on wall clocks (now()).
- withLock holds for the job's duration but has no expiry; the lease path expires_at and staleness differ. A job that joins the queue and then runs a 20-40 min body (android.mjs:156, ios.mjs:344) is judged only by pid liveness or staleMs=4h (lock.mjs:53-54). A queued job whose runner is SIGKILLed leaves a stale ticket that blocks everyone for up to one poll until pruned; but a stale *lock* of a killed job on a different host (Mac) blocks up to 4h.
- Poll cadence mismatch: withLock polls every 2000 ms (lock.mjs:68), catchup every 100 ms (catchup.mjs ~464), acquireLease every 1000 ms (hub-device :688). In a FIFO queue with position-0 gating, a 100 ms catchup poller that joins the queue makes every catch-up pass a ticket holder that blocks deploys behind it while it sits at position 0 for 5s lockWaitMs; catchup's contract is 'idle if busy, next pass' (catchup.mjs:469, :591), so catch-up must NOT enqueue (or must use waitMs 0 and cancel its ticket) or it will cut in line ahead of waiting deploys or churn tickets on every pass.
- Transient tickets from takeAnyPhone (hub-device.mjs:214 + lock.mjs:201-206/257): once deploy jobs share the queue, every `phone` pass inserts a ticket on s24 and adb queues and removes it. A real deploy waiter at position 1 sees position shift, ETAs computed from queue depth are wrong, and Event Log 'request'/'cancel' events (addendum line 75: emitted from acquireLease after the ticket rename and in finally) will log two events per held phone per poll tick (default 1 s, up to 12 per phone per --wait 2m): event-log spam and false 'timeout' semantics. Either skip events for waitMs:0 probes or add a non-enqueueing try-acquire.
- status text is pinned whole by hub-device.test.mjs:888 (nine-line deepEqual) and several regexes (:861-864); adding Peek/Reservation/ETA sections, a queue-position column, or an Event Log tail to default text output will break these and the install.sh test (:936-941 `status.locks` deepEqual []). Put new data under new --json keys and new sections only when non-empty, or update the pinned tests deliberately.
- Peek of the S26 version under a Lease: hub-device `lease s26` with --no-connect never touches adb (:158), and the peek cannot be done by status (read-only, :529, test :902 'never calls adb'). The Peek requires adb (createAsyncAdb / adb.installed). plan.mjs:230 reads the version inside withLock('adb') using sync createAdb; a Peek that bypasses the lock (reading under a Lease) must use the same hub adb server port (HUB_ADB_SERVER_PORT :156) and not start one (status's phonePresence guard, :463).
- Reservation gate semantic: gate.mjs/preflight-ios read the iPad version with NO lock (addendum line 37). A reservation that makes preflight 'wait' must not make iOS deploys that have just started ios.mjs:276 (which takes mac-ios) deadlock with a Reservation held by the same run; ios.mjs takes mac-ios twice (:276, :390), so a per-run Reservation must be re-entrant or released between the two takes.
- listLocks entry `stale` calls stale(path, owner) which for a lease checks expires_at/holder_pid and for jobs pid-liveness + staleMs (lock.mjs:42-55). A Reservation record would need its own staleness branch there; otherwise stale() falls to the job branch (age>4h) and a reservation with no pid field is treated like a job with undefined pid (Number.isSafeInteger(undefined) is false so only age is checked).
- hub-device.mjs:133 and :385 use lease_id to find waiters; once job tickets lack a lease_id (or reuse the run id), `--id` uniqueness checks and `release <id>` could match or fail to match unexpectedly. Give job tickets a distinct kind field and a synthesized id, and have status render job tickets without reading lease_id/holder/why (line :553 and :507).
- Single-instance state: `ticketCounter` is a module-level counter (lock.mjs:123) and ticket file names order by wall clock ms (:201); cross-host or clock-skewed enqueues can reorder FIFO. If the Event Log is an append-only file written from withLock/acquireLease/reclaim/releaseLease from many processes (runner jobs, catchup, hub-device, emulator), it needs O_APPEND single-write lines (<PIPE_BUF) or per-event files; lock.mjs has no existing logging dependency, and tests assert the lock dir listing (hub-device.test.mjs:878) so the log must live outside HUB_LOCK_DIR or the test updated.

### Design risks
- The catch-up parses withLock's message by regex: /host lock adb is held/ and /host lock mac-ios is held/ (catchup.mjs:469,591). acquireLease's queued-behind-waiters timeout wording is 'host lock <name> has N waiters ahead ...' (lock.mjs:251), which does NOT match. If queue-joining withLock reuses that wording, an older catch-up rethrows and exits 1 on every pass. Every timeout variant (held, and queued behind waiters) must keep the literal 'host lock <name> is held' and add a .code (withLock has none today, lock.mjs:94).
- NFR-2 skew on latest.json: device blocks are exact-keys with a frozen status enum (latest.mjs:18,111-121), and every catch-up release refuses the whole file on any extra key (catchup.mjs:342-347). FR-30's 'blocking Holds named' must go only into device.reason (at most 300 chars) or the receipt/event. A new key or a new status such as 'blocked' would blind every older catch-up to that app.
- Privacy: latest.json is anonymous for every app (access.mjs:14,40) and pages render device.reason (pages.mjs:33-35). Putting describe(owner) text into reason, which carries lease holder, free-text why, lease_id and expiry (lock.mjs:35), would publish agent and person lease details publicly. Use a coarse public reason and keep holder detail in the receipt and Event Log.
- FR-30 on Android must catch the timeout outside withLock: today only HUB_PHONE_AWAY inside the callback becomes pending (android.mjs:117-122). Moving to pending makes the android job green, so the Play upload and the private Release now run for contention-blocked builds (yml:286-325), where today they are skipped. That is a behaviour change to state explicitly.
- FR-30 is not achievable for iOS without restructuring: the build, the IPA export and the outbox copy all happen inside mac-ios (ios.mjs:276-301). Options are a separate build-only resource, or treating ios-lane contention before the build as 'skipped' or red. The store-IPA second take (ios.mjs:390) can also flip an installed iPad to failed on timeout. FR-9 same-run passthrough has to cover both takes, or the second take's timeout has to be reported at stage 'deliver'.
- With a 5 s budget the catch-up's FIFO turn is illusory: it writes a ticket, leaves after 5 s, and re-arrives at the back every 120 s or 300 s. It is served only if the Resource is free at that moment, or becomes free within 5 s while the catch-up is at the head. Back-to-back Leases, or a lease renewal right at expiry, can starve pending installs indefinitely. Consider a longer catch-up wait bounded by the 45 min watchdog (catchup.mjs:1076), or a Reservation-like standing claim for 'pending owed' work.
- Wait budget versus job timeout: android takes the adb lock only after a build of variable length (android.mjs:49-112). A fixed 20 min wait can exceed the 45 min job (yml:258), and plan's 20 min wait equals its 20 min job (plan.mjs:234, yml:196). A GitHub kill skips guarded (common.mjs:39-49), so no receipt is written. deliver-android runs only on success or failure (yml:425), so the outcome depends on how GitHub classifies a timed-out job. This is unverified here, so FR-8's 2-minute margin must be computed from the real job start.
- When a contention-pending S26 is later found 'ahead' at catch-up time, transition() writes 'skipped' with event:false (catchup.mjs:656). The run was already announced .completed with S26 pending, so no event ever reports the refusal. FR-30's 'refused' needs either an event on skip or a pending-resolution event in the Event Log.
- Completion durability for a contention-pending delivery relies on the gate's catch-up mode reading (announce.mjs:160, lib/completion.mjs:97) and on deliver publishing latest.json. Under the current policy with no completion block, device targets are never required (policy.mjs:267-269), so FR-30's 'green' is trivially COMPLETE. If completion.required.devices becomes 'lanes', a watch-mode host makes contention-pending INCOMPLETE.
- inflight.json (plan.mjs:324) holds every pending build at or below the in-flight version until deliver clears the platform (deliver.mjs:281-287, catchup.mjs:411-419). A deploy that goes contention-pending clears it at deliver-android, which is fine. But a stuck deliver leaves inflight.json for up to 6 h (catchup.mjs:58), during which the catch-up will not install the pending build even after the S26 frees.

### Design risks
- Pinned-run coexistence is real and wide: reruns keep their original tag for 30 days; pinned older withLock polls bare mkdir (lock.mjs:65-105) and ignores .queue/.reservations, and v<=1.2.25 reclaims leases as dead jobs (leaseSupport comment hub-device.mjs:110-115). The existing precedent is feature-sniffing lock.mjs source for 'export async function acquireLease' (hub-device.mjs:115); the new format needs a comparable detectable marker (queue ticket format frozen, per addendum B4).
- withLock has no error code (lock.mjs:94) and three consumers parse its message (catchup.mjs:469,591; emulator.mjs:312,342). Adding queue-joining without adding code 'HUB_LOCK_TIMEOUT' AND keeping the exact `host lock <name> is held` text breaks the catch-up (red instead of idle) and the emulator reaper; but the queued branch message (lock.mjs:251 'has N waiter(s) ahead') already differs. Fix once in a shared failure() and switch callers to error.code.
- Queue tickets are host/pid/process_start bound and are pruned by ANY acquirer poll (lock.mjs:139-146, :213): job tickets from a GitHub-killed job vanish correctly, but a Reservation written by the gate or preflight-ios process (which exits) can never be a pid-bound ticket; it must live in a separate dir (addendum B3 has this right) AND must not use hostname() for staleness. On the Mac os.hostname() is mommymac.local (mDNS-derived) so any host-equality check there is fragile.
- processStart() on macOS spawns `ps -o lstart=` (lock.mjs:134, timeout 5s) per queue ticket per poll via staleWaiter; with catch-up pollMs 100 and several job tickets this is a spawn storm on the Mac every 100ms, and if ps fails process_start is null so the ticket is instantly stale and acquireLease throws HUB_LEASE_CANCELLED 'lost its place' (lock.mjs:142,250). There is no test of the ps branch (CI is ubuntu, /proc only).
- Fake-clock tests are unsound for new code: stale() mixes injected now() with real file mtimes (lock.mjs:44) and listWaiters uses Date.now() (:164); tests rely on real timers (lease.test.mjs settle 8-30ms). hostname() and processStart() are un-injectable. New modules should take {now, host, processStart, readdir/fs} seams from the start, and the Event Log writer should take an injected clock and hostname rather than copy the lock.mjs pattern.
- hermetic() strips every HUB_* variable (test-fixtures.mjs:23-25) and replaces fetch, but the lock/lease/hub-device/emulator tests don't call it. Any new env knob (e.g. HUB_EVENTS_FILE, a Reservation grace) must be passed through the env object each test builds and must NOT be policy: CLAUDE.md says policy lives in policy.json, parsed strictly (policy.mjs), never from env/inputs; wait budgets, grace_s and reservation ceilings belong in policy.json (+ policy.test.mjs) and get injected into the pure lock lib, which today has no policy dependency.
- No append-only log, no shared atomic-write helper (4 copies: lock.mjs:117, emulator.mjs:198, catchup.mjs:183, plus store/quickdrop) and no fsync convention exist. The Event Log is the first O_APPEND writer: define one helper in a lib shared by lock.mjs and tools/device, bound line size under PIPE_BUF-ish 4 KiB for atomic appends, handle ENOENT lockDir (lockDir may not exist before first mkdir, lock.mjs:76), and cap/rotate (events.jsonl is read by nothing today; listLocks ignores non-*.lock, lock.mjs:305).
- Hub version for events: HUB_VERSION is a trap (app version). Under current/ or hub-device, hub_ref/hub version is only derivable from the release path; release dirs hold only tools/ with no .git, so releaseName() (hosts.mjs:28) cannot be reused there.
- Job tickets break lease-shaped consumers: hub-device status prints undefined for holder/why/lease_id (hub-device.mjs:553, addendum already notes), `release <id>` and the --id duplicate guard match on lease_id (hub-device.mjs:129-135,385; lock.mjs:272), and acquireLease locates its place by file name (lock.mjs:214). A kind:'job' ticket needs a synthetic lease_id or all consumers must branch on kind.
- Pending-instead-of-red (FR-30) has two different failure points: plan.mjs:229-243 (before the bump, safe to go red/blocked) and android.mjs:112-156 (after the version is spent, where a lock timeout is a red lane today). ### Design risks
- FR-30 cannot be applied to the iOS lane as written. mac-ios covers the Xcode build itself (ios.mjs:276-301), so a wait timeout means no IPA exists and the catch-up has nothing to install. The second take (:390, store IPA) feeds TestFlight, which the catch-up never does. FR-30 'pending' is only cheap for android (android.mjs:112-122), where the build is outside the lock.
- FR-30 for android needs withLock to throw a coded timeout (it has no .code today, lock.mjs:94), and android.mjs:112 needs a catch like notOnAdb. A GitHub kill at timeout-minutes writes no receipt, so the deadline has to come from the job start, which no input carries. android's lock wait starts after a variable-length build (:49-104).
- Plan behaviour on contention is unspecified for v1a. If plan's Peek/wait times out behind another deploy's Job Hold, it either goes red (today, plan.mjs:237-238) or bumps blind like 'away' (:239-241). Bumping blind moves the downgrade check to android.mjs:126, after the version is spent, and FR-30 then says refuse.
- Peek mechanics: the Lease record may name a non-default adb server port (hub-device.mjs:155-156) and a wireless adb_id that changes. A --no-connect Lease has adb_id null. The Peek must check that a server is already listening before any adb call (and blank RUNNER_TRACKING_ID) or it will start or kill a server under the lessee.
- Same-run passthrough by GITHUB_RUN_ID needs reservation idempotence. 'Re-run all jobs' reruns the gate with the same run id and a new attempt (GITHUB_RUN_ATTEMPT). The addendum's `<enqueued_at>-<run>.json` naming would make a second Reservation for one run. Key it on run id and reuse a live one.
- Reservation release: the announce job runs on Linux (yml:514) with a 10-min timeout. It can ssh 'hub-mac' (as gate/plan do, metered.mjs:81-85), but it must know the Mac user's lock dir (default ~/.cache/... on the Mac; HUB_LOCK_DIR unset), and it fails whenever the Mac is offline. plan can flip the lane to skip-lost after preflight-ios already wrote the mac-ios Reservation (plan.mjs:306-316), so that Reservation lives to its 3 h ceiling. announce only runs after the ios job (≤120 min) plus Mac queue time, so Reservations outlive the last Job Hold unless the last-hold rule (android, or ios :344/:390 depending on testflight/store.build) removes them first.
- Grace period will almost always lapse. The adb Reservation is taken in the gate, but the next adb take is plan (after preflight-ios, up to 10 min on the Mac) and then android after its build. The mac-ios Reservation is taken in preflight-ios, but the ios job starts only after plan (≤20 min) plus ios-export (≤30 min) plus the Mac queue. Each run will idle a free S26 or Mac for 10 min once (SM-C4 cost) without gaining anything.
- GitHub-side queues outside the hub FIFO: every lane has a per-repo concurrency group with cancel-in-progress false (yml:197-199, 259-261, 340-342, 378-380, 428-430, 472-474). GitHub keeps only one pending job per group, so a third same-app run cancels the older pending one. SM-1 counts this as a lost delivery, and the hub cannot see or order it.
- Wait deadlines relative to job start: steps before the hub step (checkout with fetch-depth 0 in plan yml:218-223; download-artifact in ios/deliver) eat budget. The process start of `node hub.mjs` is not the job start. The design needs an explicit per-job timeout input (hard-coded per job in mobile-deploy.yml, a hub-side change) plus a start-time source (Runner.Worker ancestor start time, or jobs API started_at through the host gh login as announce.mjs:44-50 does).
- Mixed-version window: deploy jobs on pins v1.2.26..v1.2.43 use bare-mkdir withLock and can grab a free lock past queued tickets. hub-device on an older install ignores Reservations. hub-device text status prints 'undefined' for job tickets (hub-device.mjs:553). The catch-ups switch only at the first real deliver/ios job on the new pin (deliver.mjs:295, ios.mjs:401-402).
- Event Log scope: deliver/catch-up/bucket-policy nest s3-<slug> then s3-index (deliver.mjs:249 -> s3.mjs:219). These are internal locks and must stay on the bare withLock path. A shared withLock change that logs or queues by default would put them in the queue unless the change gates on Registry lock names (adb, s24, mac-ios, emulator-N).
- Plan holds 'adb' while waiting up to 180 s for an absent phone (plan.mjs:232, policy.json:51) and while starting the server and adb-connecting. Under a Lease-aware Peek that wait must not happen while a Lease holds the S26, or plan would contend with the lessee's own connection.
