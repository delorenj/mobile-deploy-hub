# Mobile Deploy Hub

Feature list: [docs/features.md](docs/features.md).

One deploy contract for Jarad's mobile apps: Tower of Lost Things (`tower-of-lost-things`, renamed from `pile-of-dumb-things` on 2026-10-09; the S3 build folder moved with it), Green In Between (`green-in-between`) and Gruvato (`gruvato`). The hub is a library: one reusable workflow, one composite action, a Node tool and one policy file. Each app calls it from `.github/workflows/deploy.yml`, a verbatim copy of [`templates/deploy.yml`](templates/deploy.yml) pinned to the floating `@v1`, and the jobs run on the app's own repo-scoped runners (big-chungus for Linux, the Mac for macOS). The hub has no runners, no secrets and no CI of its own. Design: [docs/design-hub-v1.1.md](docs/design-hub-v1.1.md) (v1.0: [docs/design-hub-v3.md](docs/design-hub-v3.md), v2 history: [docs/design-hub-v2.md](docs/design-hub-v2.md)).

## Deploy

Every new version of an app deploys through this hub, the same way in every app repo, from any machine with `gh`, wherever the devices are:

```sh
mise run ship                      # the one command: dry run, then the real run on the same commit, then the verdict
mise run deploy                    # the primitive: a dry run; builds and checks everything; publishes, installs and sends nothing
mise run deploy --dry-run false    # the primitive, real: patch bump, publish, install where the devices are, one Bloodbank event
mise run deploy:train --dry-run false   # in the hub: Tower, then Green In Between, then Gruvato; stops at a red run
mise run ship --repo delorenj/gruvato   # in the hub: ship one app from here
```

### Ship: one command, with an optional stricter completion contract

`mise run ship` reports the completion verdict for the policy pinned by the app. **The current released-policy file has no `completion` block:** it preserves v1.2.25 behavior, with TestFlight opt-in, unavailable iOS lanes skipped, absent devices pending, no mandatory device target and no automatic rerun. A green run therefore does not prove that every device or TestFlight has received the build. The stricter contract below is deferred and must be reviewed and released separately; it is not activated by the authored release-notes work.

| Line | Exit | Means |
|---|---|---|
| `SHIP_COMPLETE <app> <version>: ...` | 0 | every target required by the pinned policy is satisfied; with no completion block, this does not require devices or TestFlight |
| `SHIP_INCOMPLETE <app> <version>: ...; owed <target>: <command>` | 4 | the run is green and something is owed; each owed target names the exact command that pays it |
| `SHIP_RECOVERY_BLOCKED ...` | 4 | a red real run spent its version and a rerun cannot fix it (below) |
| `SHIP_RED ...` | 1 | a red dry run (`stage=dry`, nothing spent), a real run red before its bump (nothing spent), or red after it and its automatic reruns |
| `SHIP_UNKNOWN ...` | 3 | GitHub never gave a verdict, or the verdict artifact could not be read: neither shipped nor red |
| `SHIP_BLOCKED ...` / `SHIP_BUSY ...` | 5 | nothing was spent: a required lane cannot run (the Mac offline, or a metered link over budget: `--metered allow`), main kept moving, or a real run is already queued or in progress |

**Deferred completion contract (not in the current policy).** An explicit `completion` block could require every lane's device (the S26 for `android`, the iPad for `ios`) and TestFlight for apps declaring `ios.store`. A device would be satisfied when installed or durably pending: `latest.json` names this exact version and catch-up is live. TestFlight would be satisfied on upload/assignment to Owner Testing. Skipped lanes or unfulfilled targets would be owed. Tests exercise this explicit future configuration without enabling it. With the current absent block, an unavailable iOS lane skips, devices are not mandatory, and TestFlight is only requested with `--testflight true` through `deploy`.

**What ship does, in order.** It takes no `--platform`, `--testflight` or `--dry-run`; only `--bump`, `--metered` and `--abandon`. It reads nothing but the policy at the hub ref the app pins and the run's own `completion-out` artifact (written by the announce job from `tools/ci/lib/completion.mjs`), so it encodes no rule of its own.
1. **Busy:** a real run queued or in progress stops it (`SHIP_BUSY`).
2. **Recover first:** a red last real run under the 7-day window that spent its version is considered before anything new is bumped. With the current policy (no completion block, zero automatic reruns), ship reports the same-version `gh run rerun <id> --failed` command rather than running it. An explicit future `completion.reruns` may permit up to three automatic attempts. A rerun checks the run's own commit out again; if a failed app hook's scripts or command changed on main, `SHIP_RECOVERY_BLOCKED` explains why that rerun cannot use the fix. The existing `--abandon <id>` option leaves that run alone and ships a new version.
3. **Dry:** when the current policy skips an offline or over-budget Mac, ship still runs its dry handoff and checks the resulting verdict. An explicit `lane_unavailable: refuse` would block on an offline runner before dispatch. A red dry run is `SHIP_RED stage=dry`; a dry verdict that owes a configured required target is `SHIP_BLOCKED`. Nothing is spent either way. If main moves meanwhile, the new tip is proved again.
4. **Real** on the commit the dry run proved, watched like `deploy` (one read every 30 s, `SHIP_UNKNOWN` only after 6 hours of no verdict), then the verdict. A real run red after its bump goes through the same recovery as step 2; a gate that refused a lane is `SHIP_BLOCKED`.

**What slice 2 adds** (not in v1.3): a durable TestFlight store pass on big-chungus (upload processing to VALID, assign, Beta App Review kept distinct, its own `latest.json` block and retries) so TestFlight can be durably pending like a device; catch-up heartbeats, so "the catch-up is live" means a recent pass, not only the mode file, with staleness escalation for a device pending too long; and a hub-owned same-version `recover` that rebuilds the owed lanes at the tag with repaired tools, which is what `SHIP_RECOVERY_BLOCKED` points at. Ship is accepted in the apps through [`templates/mise-ship.toml`](templates/mise-ship.toml) (below); conformance does not require it yet.

A real deploy bumps the patch version (`--bump minor` or `--bump major` for more), commits and tags it on `main`, builds the APK and the iPad IPA, and publishes them to the build directory ([https://s3.delo.sh/builds/index.html](https://s3.delo.sh/builds/index.html), or just `s3.delo.sh/builds` in a browser: Install APK, Install on iPad), Quickdrop (`~/quickdrop/builds`, APKs up to 120 MB, only while the S26 syncs from the LAN) and the private Release `vX.Y.Z`. It installs in place on the S26 and the iPad when they are reachable and reads the version back. **An away device is `pending`, not a stop** (so is an S26 whose `adb` wait runs out because a Lease or another deploy holds it: pending with the public reason `S26 busy`; see the Reservation paragraph below): the run goes green, the ntfy notification carries the install links (with the download's size), and a catch-up installs the build when the device is back (2 minutes on the S26, 5 on the iPad; `tools/catchup/`), never while the app is on screen. One `bloodbank.project.deployment.completed` (or `.failed`) event names each device's status (`installed`, `pending`, `skipped`, `failed`) and carries the links. `--platform android|ios` narrows it; `--metered allow` builds the iPad lane even when the Mac's metered link would go over its data budget. A deploy that failed after its bump is finished with `gh run rerun <run-id> --failed` (same version, same commit); the front door offers it for 7 days (the window of its receipts and staging), and after that a new version is the way.

The front door reads the run it started with one `gh api` call every 30 s and ends only on what the run itself reports: `DEPLOY_GREEN`, or `DEPLOY_RED` for a completed run that did not succeed. GitHub being unreachable or rate limited is no verdict: it backs off (to 5 minutes, or to the rate limit's reset) and keeps asking. Only after 6 hours without a verdict does it end `DEPLOY_UNKNOWN` (exit status 3, neither green nor red) with the run URL and the command to finish by hand (`gh run watch <id> --repo <repo> --interval 30 --exit-status`); a release dry run that ends unknown leaves `v1` where it is instead of rolling it back.

Nothing has to be at home first: the `gate` job reads the Mac's link (home, metered or offline, from tailscale, this app's own Mac runner and GitHub's view of it) and the S26 itself, and skips the iPad lane when the Mac is offline or a metered link would go over budget. The APK half never waits for the Mac (`deliver-android`), and a Mac that goes away after the gate costs the iPad lane, not the deploy: the plan probes the Mac again (`skip-lost`), and the host watchdog gives up an iPad job no runner takes within `mac.queue_limit_min` (15 minutes) instead of letting GitHub hold it for 24 hours.

**One-time setup on the devices:**
- **S26:** subscribe the ntfy app to `bloodbank` on `https://ntfy.delo.sh` (it already is). In Syncthing on the S26, set the run conditions to Wi-Fi only (Settings > Run conditions, at least for the `quickdrop` folder); the hub also writes Quickdrop only while the S26 syncs from the LAN, but the phone decides when it pulls. The first Install APK asks once to let the browser install unknown apps.
- **iPad (and an iPhone):** subscribe ntfy-ios to **`deploys`** on `https://ntfy.delo.sh`. iOS wakes only for topics the ntfy upstream gate forwards, never for the `bloodbank` firehose; the router copies every deploy event there. Bookmark `https://s3.delo.sh/builds/index.html` in Safari as the fallback.
- **GitHub app:** bookmark each app's Deploy workflow (Run workflow, untick `dry_run`).

**The taps:**
- **S26 away:** Install APK in the notification, then Download (Chrome warns that the file type can harm the device), Open, Update. On Wi-Fi at home it is shorter: Files > Quickdrop > builds > the APK > Update, or nothing at all, since the catch-up installs it within 2 minutes once the S26 is on big-chungus's adb.
- **iPad away:** Install on iPad in the notification (or Install on the build page in Safari), then Install in the iPadOS prompt.
- **Back home:** nothing. The catch-up installs or confirms each pending build and sends one notification per device; it waits while the app is on screen.

### When something else replaces the iPad build

A deploy installs a development-signed build on the iPad with `devicectl`. If the same bundle id also ships through TestFlight or the App Store (Tower, Gruvato and Navi share one), a TestFlight update, or a tap in the TestFlight app, replaces that build with whatever TestFlight holds, which is usually older: the two channels run on different build numbers. `latest.json` still says `installed`, so the iPad quietly shows an old version until the next deploy. Tower's own log shows it: 0.3.18 (23) was on the iPad on 2026-10-30, and on 2026-11-02 the catch-up logged "installed over 0.3.0 (9)" (TestFlight build 9) when it put 0.3.19 (24) there.

The iPad catch-up now looks again. On each pass, for every app whose iOS build is `installed` (or `skipped`), it reads the iPad once and compares it with `latest.json` (version first, then build):

- **Older on the iPad:** the build was displaced. It is reinstalled in place from the Mac's outbox (or downloaded off a metered link), exactly like a pending build: same sha256 check, same wait while the app runs (up to 45 minutes), same readback, one event. `latest.json` keeps `installed` and records `by: catch-up` with the reason `repaired: displaced by 0.3.0 (9)`; the notification says it was repaired.
- **Equal:** nothing. **Newer, or the app is gone (you deleted it):** nothing but a log line. A device that gave up (`failed`) stays silent until `catchup.mjs retry`.
- **Watch mode:** logs `HUB_CATCHUP_WATCH ... would repair`, installs nothing.
- **Flap guard:** an app is repaired at most 3 times per UTC day on a host (`iosRepairsPerDay`); after that the pass only logs `already repaired 3 times today`. A repair that fails logs `HUB_CATCHUP_REPAIR_FAILED`, counts toward the limit and is tried again on a later pass.

It never removes the app, clears data or downgrades. This only shortens the damage: TestFlight can still replace the build between passes (5 minutes). The fix that ends the fight is a separate development bundle id (`store_bundle` in the policy, as Green In Between does): the dev build then lives beside the TestFlight app and nothing replaces anything. For Tower that changes its frozen owner identity and the saves in it, so it is the owner's call, not the hub's.

## Deploy policy

The rules every deploy obeys live in one file in this repo: [`tools/ci/policy.json`](tools/ci/policy.json). The `gate` job reads it from the exact tag the run pins — never from a workflow input, an environment variable, an app manifest or a hook — so the front door, `gh workflow run`, the GitHub mobile app and every rerun all run the same rules. Only the hub can change a rule; apps inherit it through the `@v1` pin and never carry deploy policy of their own.

What it pins: bump levels (patch by default, never "none"), one Bloodbank event per run attempt, manifest schema 2, the caller allowlist (`callers.accept`, the hashes of accepted `templates/deploy.yml` versions), pinned self-hosted runner labels, absent-device handling (`pending`, never a stop), the downgrade refusals, the delivery targets (S3, Quickdrop, the private Release), each app's signer and package pins (`apps.<repo>.android.editions` pins an extra Android edition and whether it may be public; `store_package` and `store_upload_sha256` pin the Play app and its upload key, see "A separate Play app"), and the Mac's metered data budget. There is **no `completion` block** in the currently deployed v1.2.25 policy or in this source policy; the optional stricter contract below is deferred:

```json
"completion": { "required": { "devices": "lanes", "testflight": "store" }, "lane_unavailable": "refuse", "reruns": 1 }
```

If adopted in a separate policy release, `required.devices: lanes` would require each lane's device; `required.testflight: store` would require TestFlight for every `ios.store` app; `lane_unavailable: refuse` would stop a real run before its bump if the required Mac lane cannot run; and `reruns: 1` would permit one automatic same-version rerun in ship. Until that separate release, absent `completion` means `devices: never`, `testflight: never`, `lane_unavailable: skip`, `reruns: 0`; the caller's TestFlight input remains opt-in. The parser and tests support both contracts, but the release-notes change does not activate the stricter one.

### Queue tuning (`queue` block)

One strict block that each Queue story grows by its own keys only (an unknown or missing key refuses the policy). Callers never pass these and no env or input overrides them; a writer stamps what governs others into its record (`deadline_at`), and changing a value is a hub release.

- **`wait_margin_min`** (2) and **`hold_allowance_min`** (`plan`, `android`, `ios`; whole minutes): a deploy job that waits for a device in the Queue stops waiting at `job_start + timeout - margin - allowance`, so it can report its own reason before GitHub kills it at `timeout-minutes` (a killed job ends `cancelled`: no `finally`, no `deliver-*`). The allowance covers every hold the job still has to take; `ios` takes `mac-ios` up to twice. `timeout` is `HUB_JOB_TIMEOUT_MINUTES`, set in `mobile-deploy.yml` beside each of those jobs' `timeout-minutes` (a test keeps the two equal), and `job_start` is the start of the nearest `Runner.Worker` ancestor, else the tool's own start. A job with no allowance (`deliver-*`), a catch-up and a person at a shell keep their caller's timeout. The wait's ticket and events carry the deadline as `deadline_at`, and its timeout reads `gave up after N min, ahead of this job's M-minute timeout`.
- **`grace_min`** (10) and **`reservation_ceiling_min`** (180; whole minutes): a deploy run reserves its devices when it starts, so its build never loses its place to whoever asks while it compiles. The gate reserves `adb` when the run will install to the S26 (an iOS-only run reserves nothing there), and `preflight-ios` reserves `mac-ios` on the Mac's own disk. A Reservation is the directory `<name>.reservations/<owner>--<repo>--<run>/` beside the lock (an older pinned hub never sees it: it is no `*.lock`), holding `reservation.json` (`{format, run_key, repo, run, reserved_at, expires_at, grace_ms}`, written once) and, once someone observes a free lock, `grace.json` (written once). The record stamps both values as absolute times, so readers never apply their own, and a Reservation is live only until `expires_at` (the ceiling). A rerun reuses its live Reservation. In `queueView` a Reservation is listed at its `reserved_at`; it is hidden while its run has a live ticket, and that run's Job Holds take a ticket named for the Reservation's `reserved_at` (`enqueued_at` keeps the real time), so they are served at its place and never wait behind it. Only the first Reservation in line blocks, and only until its one-time grace is over: the first acquirer or try that finds the lock free while an unasking head Reservation stands starts the grace (`grace.json`, one `grace` event), the rest wait until `grace_started_at + grace_ms`, and after that the Reservation keeps its place but blocks nothing. A Reservation past `expires_at` is renamed to `.released-<key>-<ms>` by whichever acquirer prunes it first, and only that winner appends `expiry`. The events are `claim`, `grace` and `expiry` (`hold_kind: reservation`). A Reservation that cannot be made is logged as `HUB_RESERVATION_FAILED` and never fails the job.

A Reservation ends when the run is done with the device (`releaseReservation` in `lock.mjs`): the directory is renamed to `.released-<key>-<ms>` and deleted, the process whose rename won appends one `release` event (`hold_kind: reservation`), and a grace stamp that lands later fails with ENOENT and is ignored. The release is renamed away before the run's lock is freed (`withLock`'s `endsReservation`), so nobody ever sees a free lock with a finished run's Reservation first in line. Who releases when: the `android` lane on success or an away S26 (inside its `adb` hold), and after a timed-out `adb` wait (outside any hold: the S26 is busy, the delivery goes `pending` with the public reason `S26 busy`, the run stays green and the Play upload and Release proceed; the blocking Holds go only to the lane's receipt as `contention`, which the bucket copy drops, and to the Event Log as a `timeout` event with `reason: delivery-pending`), the `ios` lane on success (inside its last `mac-ios` hold: the second take for a store build), a lane that ran out of wait for `mac-ios` keeps it (iOS has no `pending` on contention: the build and the lane hold are one, so the `ios` job fails with `HUB_LOCK_TIMEOUT`, the receipt's `contention` `{lock: mac-ios, reason: ios-lane-contention, blocked_by}` names the holder and the waiters ahead, and the Mac's Event Log gets the one `timeout` event with `reason: ios-lane-contention`; a timeout of the second, store-IPA take is reported at stage `deliver` with a failed `store` record and the iPad's install standing; the bucket receipts and the Bloodbank event say only `mac-ios busy`, see `publicReason` in `lib/receipt.mjs`), `plan` when the run skips the Android lane, and `announce` as the backstop for any lane that ended `success` (`adb` locally; `mac-ios` over `ssh hub-mac '~/.local/bin/hub-device reservation release --run <key> --name mac-ios'`, never `rm`). A lane that failed never releases: grace and the ceiling end it, so `gh run rerun --failed` is served at the original place (a step that fails after the lane's last hold, such as the Play upload, finds the Reservation already released: the lane releases inside its hold so the lock is never free with a finished run's Reservation in line). A Mac whose installed `hub-device` has no such verb yet is logged as `HUB_RESERVATION_RELEASE_SKIPPED` and left to the ceiling (`reservation_ceiling_min`); a release that fails is `HUB_RESERVATION_RELEASE_FAILED` and never fails the job. `hub-device reservation release --run <owner--repo--run> [--name adb|mac-ios] [--json]` does the same by hand: it prints `HUB_DEVICE_RESERVATION_RELEASED <name> <key>` per release or `HUB_DEVICE_RESERVATION_NONE <key>`, and exits 0 either way.

**Leases cannot starve the Queue (`deploy_target_lease_max_min`, 60; whole minutes).** A Lease on a deploy target (`adb`, the S26's lock, and `mac-ios`) may run at most this long in total, counted from its start: `acquireLease` refuses a longer one (`HUB_LEASE_TOO_LONG`) and `hub-device lease s26 --for 2h` exits 2 naming the cap and pointing at `s24` or an emulator (`hub-device lease phone` over the cap skips the S26; `s24`, emulators and every other lock keep only the 48 h limit). A Lease is extended only through `extendLease(name, id, {forMs})` in `lock.mjs`, which moves `expires_at` later by `forMs` and appends one `extend` event. It refuses with `HUB_LEASE_EXTEND_REFUSED`, writing nothing, while any entry in the Queue that blocks is waiting (the message names each waiter with its place; a Reservation past its grace does not block), at or after the Lease's expiry, and past the cap. The waiter check reads every queue the Resource is served from (`waitersBehind` in `lock.mjs`, read only): the lock's own queue, where a Pool request's ticket counts once per member queue, minus the extender's own ticket and any Pool ticket whose request already holds a member (it is served); and, for an `emulator-<n>` slot, the `emulator` gate, whose live holder is next for a slot (position 1, unless it is the extender or already holds a slot) and then its queue. A refusal names the own-queue waiters as before and the gate's as `in the emulator line <n>. <holder> (<why>)`, joined with `; `. `updateLease` changes metadata or moves expiry earlier, never later. Every owner rewrite first checks that the lock is still the writer's (the lease id, and the directory inode a Lease records as `lock_ino` when it is taken) and otherwise throws `HUB_LEASE_LOST` without writing. The `hub-device extend` verb is v1b.

**The catch-up waits its turn (`catchup_attempt_s`, 5; `catchup_pending_wait_min`, 30).** The catch-up enqueues on `adb` (the S26 pass) or `mac-ios` (the iPad pass) as a `hub-job` only when it has a pending build for that device. A build a deploy marked `S26 busy` (a contention-pending build) stays in line for its turn: the pass waits up to `catchup_pending_wait_min`, bounded by the 45-minute pass limit less a 10-minute reserve for the download, install and readback, but never shorter than the short attempt (so the shipped 30 minutes always fits, and a pass that starts late still makes its attempt). Any other pending build (the S26 was away) makes only the `catchup_attempt_s` attempt. A wait that runs out is a coded `HUB_LOCK_TIMEOUT`: the lock removes the ticket and writes one `timeout` event with `claimant.kind: hub-job` and `reason: catchup-idle`, and the pass logs `HUB_CATCHUP_IDLE` naming who held the lock and ends without an error; a ticket an operator removed is `HUB_LEASE_CANCELLED` and idles the same way. The ticket and every event of that hold (`request`, `acquire`, `timeout`/`cancel`, `release`) carry `delivery {repo, run, version}` (any Queued `withLock` caller may pass `delivery`; events carry the key only when given). While the catch-up's ticket waits, `extendLease` refuses to extend a Lease on that device. After a long wait the hold reads `inflight.json` again before it installs, because a deploy may have started meanwhile.

**The enqueue ETA (`eta_window_days`, 30; `eta_low_data_min_holds`, 20; positive whole numbers, AD-18).** Every waiter on a Queued lock (a Lease, a deploy job, the catch-up) is given an ETA range when it enqueues, from one pure function, `eta()` in `tools/ci/lib/eta.mjs`, that the wait line (Story 4.2) and `hub-device status` (Story 4.3) share (`status` asks it through `waiterEtas` in `lock.mjs`: one windowed read of the Event Log for all waiters, a read-only observer view). It returns `{lo_ms, hi_ms, low_data}`: the 25th and 75th percentiles of matching past holds in the last `eta_window_days` of the Event Log (`release`, `reclaim` and `force-release` with a `held_ms`; a reclaim counts to the job's last `alive` touch), added along the Queue: the holder's remaining time (only past holds longer than it has already held count) plus each blocking entry ahead. A Job Hold matches past holds of the same repo and job; a Lease takes its start plus the share of its `for_ms` that past agent Leases used (25th to 75th percentile), never later than its expiry; a blocking Reservation adds 0 to its grace left. An entry with fewer than `eta_low_data_min_holds` matching holds widens to its stated duration (the Lease's `for_ms`, the job's `hold_allowance_min`) and sets `low_data: true`; with no stated duration the total `hi_ms` is the time left until the waiter's own `deadline_at` (null without one); a job holder past its whole allowance counts as unknown too. The ETA is stored in the waiter's ticket (`eta`) and in its `request` event, computed once before the ticket lands, so the actual wait can be compared with what the waiter was told (SM-4). It never fails or delays an enqueue: an error records `eta: null` and logs one `HUB_ETA_FAILED <name> <reason>` line. Tries and Pool-level requests have no ticket and no ETA.

**The wait line (FR-16, AD-18).** Every waiter on a Queued lock prints `HUB_LOCK_WAIT <name> held by <holder> position=<n> eta=<lo>-<hi>[ low-data]` through its own `log`: the job log for a deploy job or the catch-up, stderr for `hub-device lease --wait` (a successful `lease` still prints only `export` lines on stdout). One reporter in `lock.mjs` (`waitReporter`) serves `acquireLease` and the Queued `withLock` path, so every Claimant kind gets the same line. `<holder>` is the current owner as before, `position` is the blocking entries ahead of the waiter's ticket plus one (1 means next in line), and the ETA text is `formatEta()` in `eta.mjs` (the one text `hub-device status` reuses): each bound is `<s>s` under a minute, `<m>m` under an hour, otherwise `<h>h<mm>m`; ` low-data` marks a widened range; an unknown upper bound is `?` (`eta=2m-?`) and an ETA that failed is `eta=?`. The first poll prints, using the ETA computed at enqueue. After that the ETA is recomputed (one owner read, one observer view, one windowed read of the Event Log) only when the position changed or 5 minutes have passed since the last computation, never on every poll, and a line prints only when the position changed or the range moved from the last printed one by more than a minute on either bound (`etaMoved()`). The 5-minute refresh (`ETA_REFRESH_MS` in `lock.mjs`) and the one-minute move (`eta.mjs`) are fixed constants, not `policy.json` keys, so a stable wait prints about once per 5 minutes at most and only when the range really moved. A failed recompute logs one `HUB_ETA_FAILED` per waiter and the wait goes on with `eta=?`. Tries and Pool-level requests have no wait line, and a lock that is not Queued (`s3-*`, `s3-index`, `emulator-reaper`) keeps its single `HUB_LOCK_WAIT <name> held by <holder>` line.

**A newer installed build is refused with a name (FR-30, AD-15).** When the device already runs a newer build than the pending one (`HUB_CATCHUP_AHEAD` on the S26, `HUB_IPAD_NEWER` on the iPad), the catch-up records `skipped` as before and, in live mode only, unless the record reports `changed: false` (`latest.json` already said it), appends one `refused` event on that device's lock (`adb`, `mac-ios`) to its own host's Event Log, with `claimant.kind: hub-job`, `reason: newer-installed`, `delivery {repo, run, version}`, `installed` (the version on the device), `installed_by` (the Leases that held the lock since the build went pending, each `{holder, lease_id, acquired_at}`, the first 10 in acquire order with `installed_by_more` counting the rest), `pending_since` and `pending_from`. The window starts at the deploy's `delivery-pending` timeout for that build (`pending_from: pending-event`), else at `latest.json`'s `device.since` (`pending_from: latest.json`); a Lease counts when its hold overlaps the window, so the Lease that blocked the deploy and then installed the newer build is named. A pointer a newer deploy moved still counts as a refusal (the device does run a newer build); the Mac's record over ssh reports no result and counts as taken, and a repeat there is not reachable because a skipped build never comes back as `ahead`. With no Lease in the window, or an unreadable log, `installed_by` is `unknown`. Watch mode logs `installed by <holder> (lease <id>)` on its `HUB_CATCHUP_WATCH` line and writes nothing. Holder names stay in the Event Log and the host's own log line: `latest.json`, the pages, the receipt copy in the bucket and bus events keep the coarse reason (`the S26 runs X, ahead of this build`). `lock.mjs` has the readers and the writer (`leaseHoldersSince`, `deliveryPendingEvent`, `noteRefused`), so any Queued lock can name its Lease holders over a window. A skipped build is final: it is never installed or refused again, and only `retry` restarts a `failed` or `pending` device.

### TestFlight groups, the iOS version train and the 90-day clock

An app that ships to TestFlight (its manifest declares `ios.store`) may carry one more block in its `apps.<repo>` entry. Without it nothing changes for the app: Owner Testing, and the iOS marketing version is the deploy's own.

```json
"testflight": { "groups": ["Owner Testing"], "train": "minor" }
```

- **`groups`** (1 to 8 beta group names, default `["Owner Testing"]`): where the app's `ios.store.assign` hook puts each build. Internal and external groups both go here. The hub never calls Apple for this itself: it hands the list to the hook as `HUB_TESTFLIGHT_GROUPS` (comma-separated, taken from this policy for the repository and from nowhere else), writes it into the store receipt (`store.groups`), and words the completion reason and the Bloodbank delivery (`TestFlight Owner Testing, Client Review`, capped at the schema's 120 characters) from it. A group name is plain words (letters, digits, spaces and `. _ ( ) & ' -`, at most 64 characters, no comma). Adding a group that does not exist yet in App Store Connect is the app hook's failure to report, not the hub's, so list an external group only after it has been created and its review submitted.
- **`train`** (`patch`, the default, or `minor`): how the iOS marketing version moves. With `patch` it is the deploy's version, as always. With `minor` it is `X.Y.0` of the deploy: `0.3.7` ships to TestFlight as `0.3.0`, and only a minor or major bump moves it (`0.4.0`). The build number keeps climbing on every deploy (the app's `ios_build`, as before), which is what App Store Connect needs to accept a new upload under the same marketing version. Apple's Beta App Review is per marketing version, so patch deploys under one `X.Y.0` reach external testers without a new review, and a minor bump is what asks for one. The train applies to the store (TestFlight) build only: the iPad device build, `latest.json`, the OTA page, the catch-up and the tag keep the deploy's own version, and Android keeps its patch versions. The first deploy on a train should be a minor bump, so the marketing version is above anything already uploaded (Navi: `0.3.0`, above the `0.2.x` builds already in App Store Connect); a patch deploy on a fresh train would otherwise try to upload a marketing version Apple has already closed.

What the hooks see (all of them, from `plan` onward): `HUB_VERSION` (the deploy), `HUB_IOS_VERSION` (the train's marketing version; equal to `HUB_VERSION` for a `patch` train), `HUB_IOS_BUILD`, and `HUB_TESTFLIGHT_GROUPS`. A hook that stamps `CFBundleShortVersionString` reads `HUB_IOS_VERSION` for the store build; the hub checks the store IPA against the same value. A local run (`hub.mjs plan --ios-version 0.3.0`, or `HUB_IOS_VERSION`) may name the version itself.

**Beta review state, in the receipt.** An app may declare an optional `ios.store.review` hook. After `assign` it prints one line of JSON, `{"state": "...", "detail"?: "..."}`, where `state` is one of `NOT_REQUIRED` (only internal groups), `NOT_SUBMITTED`, `WAITING_FOR_REVIEW`, `IN_REVIEW`, `APPROVED`, `REJECTED`. The hub records it in the store receipt (`store.review`), logs `HUB_TESTFLIGHT_REVIEW`, and appends `(beta review: STATE)` to the completion reason. It is information and never a gate: a hook that fails or answers nonsense records `UNKNOWN` and a warning, and the deploy stays green because the build is uploaded and assigned. What it does not do yet (slice 2): `latest.json`, the Bloodbank event and the completion verdict do not distinguish "uploaded" from "testers can install"; the event schema has no field for it, so that needs a schema change first. The state is in the receipt and the reason text until then.

**The 90-day expiry.** A TestFlight build stops being installable 90 days after its upload, for internal and external testers alike, and Apple does not warn the app. Anything that testers rely on must be rebuilt and re-uploaded before then. The rule of thumb is a deploy at least every 60 days (at least one patch deploy per `X.Y.0` train, which costs no new beta review); the hub does not create that clock. It is a recurring job, so it belongs to a Candybar manifest in the app's own repo that runs `mise run deploy --dry-run false` (or states why it did not), not a cron entry or a hub timer. Until the app has one, the receipt's `store.version`/`store.build` and the `HUB_TESTFLIGHT_STATE` line of the last deploy say how old the newest build is.

### Separate bundle ids for the iPad build and TestFlight

An app that ships both to the iPad (the `devicectl` development install) and to TestFlight must not use one bundle id for both. One id is one app slot on the iPad, so the TestFlight app can install an older build over the hub's, and the catch-up repair and TestFlight's auto-update can keep displacing each other (Tower, 2026-11-02). The rule, checked by the `gate` job before any version is spent:

- **Which apps it covers.** An app with an iOS lane that has a store lane, meaning its manifest declares `ios.store` (the hub's one definition of a TestFlight app) or its policy entry carries a `testflight` block. Either signal is enough; the manifest is the one that catches Tower and Gruvato, which have no `testflight` block. The policy parser applies the `testflight` half too, so a policy edit cannot add such an app on a shared id.
- **What it demands.** `apps.<repo>.ios.store_bundle` is pinned and differs from `apps.<repo>.ios.bundle`. Green In Between is the model: device `io.lasertoast.greeninbetween.spike`, store `io.lasertoast.greeninbetween`. A shared id (no `store_bundle`, or one equal to `bundle`) refuses with `HUB_GATE_REFUSED bundle split`.
- **Direction.** The device bundle is the one that changes and takes the suffix. `store_bundle` keeps the App Store Connect record id, which Apple never lets change. What the policy can check is that `store_bundle` is not the device bundle plus a suffix (that is the wrong way round, and the parser refuses it); any other pair of different ids passes.
- **Staged.** `shared_bundle_allowlist` names the apps that have not migrated yet, each with `since` (the date it was listed) and a one-line `reason`. Today: Tower, Gruvato and Navi, listed 2026-11-18, pending MOBI-16 (an owner decision per app). For a listed app the gate logs one `::warning::HUB_POLICY shared_bundle ...` line and goes on. An app leaves the list in the same hub release that pins its new `store_bundle` and device bundle; from then on a shared id refuses. A listed app that already has a separate store bundle only warns that its entry can be removed, and a test fails if the policy ships such an entry.

```json
"shared_bundle_allowlist": { "delorenj/gruvato": { "since": "2026-11-18", "reason": "Not migrated: the iPad dev build and TestFlight share sh.delo.gruvato (MOBI-16, owner decision)." } }
```

The catch-up repair (TOLT-152) stays as the safety net for the apps still on the list.

**Changing a rule, once, for every app:**

1. Edit `tools/ci/policy.json` and its test in this repo, and add a `## vX.Y.Z` section for the release to `docs/hub-releases.md` when readers of the tag need to know something (`mise run release` puts that section into the tag annotation, above the dry-run lines: `git show vX.Y.Z`; a release with no section is annotated as before). Every annotation also carries a `Roll back:` line, computed from where `v1` pointed before the release started (never "the previous version number": a red release moves `v1` back, so a tag can exist that `v1` never stood on), naming the tag to move `v1` back to and to run `mise run hosts:install` at; the run logs it as `RELEASE_ROLLBACK`, and it reads `none` when `v1` is new.
2. `mise run release`: it checks a clean tree, runs `mise run check` and `mise run conformance` (every app's caller hash, manifest and out-of-hub drift), tags `vX.Y.Z`, moves `v1`, and proves the release with one strict dry run per app in the policy (Tower, Green In Between, Gruvato, Navi, Earshot, Shortwave) — moving `v1` back if any is red.

Apps need no edit for a policy change: their callers pin `@v1`. A caller changes only when the template itself changes, and the new template's hash joins `callers.accept` in the same release, so moving `v1` never refuses a caller that has not been updated yet.

**Adopting the policy in a new app:**

1. Copy `templates/deploy.yml` verbatim into `.github/workflows/deploy.yml`; it pins `@v1`, and the gate hashes the caller, so never edit it.
2. Write `tools/ci/mobile-deploy.json` (schema 2) and register the app's own repo-scoped runners (Linux on big-chungus, macOS on the Mac).
3. Add the `mise run deploy` task that fetches this repo's [`tools/deploy.mjs`](tools/deploy.mjs) at the pinned ref, and the `ship` task: copy [`templates/mise-ship.toml`](templates/mise-ship.toml) verbatim (only comments may differ; conformance compares it).
4. One hub release adds the app to `apps` and its caller hash to `callers.accept`.
5. Put the deploy sentence in the app's `AGENTS.md` (see the skillex `mobile-devex` skill) so its agents follow the same rule.

Everything out-of-hub is refused or retired: no app path may bump a version, mint a tag, `gh release create`, upload to TestFlight or install a release build on a device.

### A separate Play app (MOBI-18)

The Android twin of the bundle split above. The sideload APK the S26 gets and the app Play serves can be two different apps: Green In Between's device APK is `io.lasertoast.greeninbetween.spike`, signed with a debug key, while its Play app is `io.lasertoast.gib`, signed with an upload key. The hub uploads to Play under the Play app and holds the bundle to it. An app with no `store_package` uploads under its device package exactly as before (Gruvato, Tower).

- **Policy** (`apps.<repo>.android`). `store_package` is the application id Play serves; it differs from `package` and from every edition's package. `store_upload_sha256` is the lowercase SHA-256 of the Play upload certificate and is required with it; it is never the device `signer_sha256`. Both or neither: the parser refuses one without the other.
- **What the hub tells the bundle hook.** The app's `android.bundle` hook (run with `--play`, dry runs included) gets these variables, the same for every app, and the hook builds and signs with them: `HUB_PLAY_PACKAGE` (the store package, else the device package), `HUB_PLAY_UPLOAD_SHA256` (when the policy pins one) and, when the manifest declares `android.bundle_signing`, `HUB_PLAY_SIGNING_KEY_REF`, `HUB_PLAY_SIGNING_ALIAS_REF`, `HUB_PLAY_SIGNING_PASSWORD_REF`. They are `op://` references, never values: the hub does not read the secret and the hook does its own `op read`. The hub sets exactly these names on the bundle hook and clears them everywhere else.
- **What the hub checks after the hook** (a split app, in the android job and again before the upload, with `lib/aab.mjs`, no bundletool): the base manifest's package is the store package, its versionCode is the planned code, the jar signature is intact with no unsigned entries, and there is exactly one signer whose SHA-256 is `store_upload_sha256`. Anything else fails closed before Play is contacted, with `HUB_PLAY_BUNDLE_REFUSED package|versionCode|signature|signer`. A pass logs `HUB_PLAY_BUNDLE_OK <package> versionCode=<n> upload_sha256=<sha>`; `HUB_PLAY_TARGET` names the package every `--play` run is aimed at, and `HUB_PLAY_BUNDLE_UNCHECKED` says an app without a split has its bundle left to Play.
- **The upload.** The Play edit, the bundle upload and the track assignment all name the store package, and the `android-play` receipt (`play.package`, and its note) says so. A dry run does steps one and two (hook, verification) and the keyless token exchange; it never contacts Play.
- **The first bundle of a new Play app** goes up through the API like every other: create the app in Console, run `tools/play-publisher.sh <owner/repo>` and invite the service account it prints, and the hub lane uploads from the first build on (proven on io.lasertoast.tolt, 2026-11-23). A draft app's release lands as a draft (`PLAY_DRAFT_APP`). To bring a second app onto this: pin `store_package` and `store_upload_sha256` in `policy.json`, add `android.bundle_signing` (op:// refs) to its manifest, have the bundle hook read the `HUB_PLAY_*` variables, and `mise run release`.
- **The Play publisher (any app).** `tools/play-publisher.sh <owner/repo>` gives the app its own keyless publisher: a service account in the shared `hub-play-publishers` project that only that repo's Actions can impersonate (a Workload Identity provider locked to the repo and owner ids), and sets the repo's `GCP_WIF_PROVIDER`, `PLAY_SA_EMAIL` and `GCP_PROJECT_ID`. It is idempotent. The one manual step it prints: invite the account in Play Console (Users and permissions) with release rights on that app.

## The build directory

App authors can add optional, structured, tracked [release notes](docs/release-notes.md) for the next planned version. The hub snapshots the full range since the previous published build and publishes one canonical per-version record to the build page and private Release; existing apps without notes keep working with an honest missing-notes label.

MinIO bucket `builds` (private by default; see [private-device-builds.md](docs/private-device-builds.md): only public editions, every app's pointers, an iOS-lane app's over-the-air objects, opted-in device editions and the root index are anonymous, no listing; written only from big-chungus over `127.0.0.1:9012` by the MinIO user `mobile-deploy-hub`, whose keys are the DeLoSecrets item "MinIO builds writer (mobile-deploy-hub)", read with `op read` at call time into the `mc` child's environment only):

```
builds/index.html, index.json                    every app: newest version, device states, install links
builds/<slug>/index.html                         Install APK, Install on iPad, device states, sizes, commit, run, history
builds/<slug>/latest.json                        the delivery contract (tools/ci/lib/latest.mjs), read by the catch-up
builds/<slug>/inflight.json                      a real run between plan and deliver
builds/<slug>/ios/manifest.plist                 the one OTA manifest, always the newest IPA
builds/<slug>/<X.Y.Z>/<slug>-<X.Y.Z>-<code>.apk, <slug>-<X.Y.Z>-<build>.ipa, icon-57.png, icon-512.png, receipt-android.json, receipt-ios.json
builds/<slug>/editions/<edition>/index.html, latest.json   a public extra edition only: one APK link for Obtainium, the current version
builds/<slug>/editions/<edition>/<X.Y.Z>/<slug>-<edition>-<X.Y.Z>-<code>.apk, .apk.sha256, receipt.json
```

Device APKs, their checksums, receipts and release notes, and an Android-only app's page are **not** anonymous (MOBI-17). Every app's `latest.json` and `inflight.json` are: they name a build and never grant it. The hub reads private objects with its writer keys (SigV4) and hands a person a presigned link (7 days, `private, no-store`) in the deploy notification. The bucket policy is generated from `tools/ci/policy.json` into `tools/ci/bucket-policy.json`; `mise run bucket-policy` checks it and the live bucket, `mise run bucket-policy:apply` applies it (after the release and `mise run hosts:install` when the change makes something private).

`inflight.json` names the platforms a real run builds; each deliver job clears its own, and the catch-up holds every older pending build of those platforms until then. A device block's package, signer and bundle must be the policy's pins (`tools/ci/policy.json` `apps`), or the catch-up refuses the file.

## Use it from an app

1. Hub Actions access is `user` (set once: `gh api -X PUT repos/delorenj/mobile-deploy-hub/actions/permissions/access -f access_level=user`).
2. Register a Linux runner on big-chungus (started through `runsvc-op.sh`, so jobs have `OP_SERVICE_ACCOUNT_TOKEN`) and a macOS runner on the Mac (LaunchAgent through `~/actions-runner/runsvc-op.sh`, which reads the service-account token from the login keychain; never a file).
3. Copy [`templates/deploy.yml`](templates/deploy.yml) to `.github/workflows/deploy.yml` (only comment lines may differ: the gate hashes the normalized file), write `tools/ci/mobile-deploy.json` (below) and the shared `mise run deploy` task, which fetches [`tools/deploy.mjs`](tools/deploy.mjs) from this repo at the ref `deploy.yml` pins (`v1`) and runs it.
4. One hub release adds the app to `apps` in `tools/ci/policy.json`.

The `REAL` in a real run's title is how the front door finds the last real run. Callers pin `@v1`; inside the hub, every `actions/hub@` ref is one exact tag, so a run and its reruns use one hub version. `mise run release -- X.Y.Z` flips them, tags, moves `v1`, and proves the release with one strict `--dry-handoff true` dry run per app (the iPad proof, once per hub version), moving `v1` back if any is red.

| `android.bundle`, `bundle_artifact` | the Play AAB, used with `--play` (uploaded to the policy's `store_package` when the app has one, else its device package; the hook gets `HUB_PLAY_PACKAGE` and friends, see "A separate Play app"): a dry run builds it and mints the Play token through the caller's `vars.GCP_WIF_PROVIDER` and `vars.PLAY_SA_EMAIL` (the keyless exchange, proven before a version is spent) and never contacts Play; a real run uploads it to the `internal` track as a `completed` release, so testers get it at once (other tracks default to `draft`; the workflow's `play_status` input, empty by default, overrides either). | `ios.bundle`, `device`, `device_artifact` | the Mac hook that leaves an unsigned `.xcarchive` (the hub exports it) or an `.ipa` in `$HUB_OUT/ios` |
| `ios.export`, `archive`, `receipt`, `prepare` | optional Linux half (Tower's Godot export), handed to the Mac |
| `ios.store.preflight`, `ios.store.state`, `ios.store.review` | optional hooks (v1.3). `preflight` runs on the Mac in `preflight-ios`, before plan spends a version: the store toolchain the upload hook needs (its Xcode pin). `state` prints one line of JSON, `{"present": true\|false, "version", "build", "state"?}`, for the planned `HUB_IOS_VERSION` and `HUB_IOS_BUILD`: `present` means App Store Connect has that exact build, so upload is skipped and assign still runs; an answer about another build fails the step. `review` runs after `assign` and prints `{"state", "detail"?}` (Apple's beta review state for the build; see "TestFlight groups, the iOS version train and the 90-day clock"); it is recorded in the receipt and never fails the deploy |
| `ios.store` | the TestFlight lane, owed by every run whose iOS lane is in scope (the gate derives it; `--testflight` is no longer read). Hooks are shell commands from the committed manifest, run under `bash -eo pipefail` in the app root with `HUB_OUT`, `HUB_DRY_RUN`, `HUB_VERSION`, `HUB_ANDROID_CODE`, `HUB_IOS_BUILD`, `HUB_IOS_VERSION`, `HUB_TESTFLIGHT_GROUPS` (the iOS lane's hooks), `HUB_TEAM` set, and throwaway `GITHUB_ENV`, `GITHUB_OUTPUT`, `GITHUB_PATH` files. Store, GitHub, OIDC and MinIO credentials never reach a hook. Unknown keys, non-string hooks and paths outside the checkout are rejected; schema 1 is gone. Devices (the S26, the S24, the iPad, the Apple team and signer, the Mac's ssh alias `hub-mac` and tailscale peer, big-chungus's staging) live once, in [`tools/ci/devices.json`](tools/ci/devices.json). Deploys read `android` (the S26) alone; the extra phones in `android_extra` are `hub-device`'s.

## Devices

Two phones are shared by many repos and no one owns them: the S26, which deploys install on, and the S24. Each leases under its own host lock (`~/.cache/mobile-deploy-hub/locks/`, or `$HUB_LOCK_DIR`) — the S26's lock is `adb`, the one a deploy takes for the length of its job, so a lease and a deploy still exclude each other; the S24's is `s24`. `hub-device` takes a lock for a person or an agent for as long as they ask. A lease outlives the command that took it and ends at `release` or at its `--for` expiry; a lease whose `--pid` process is gone (or is now another process) is reclaimed like a dead job. Waiters for a lease queue first in, first out (`<name>.queue/` beside the lock); a deploy keeps polling its lock as before. A deploy itself takes the `adb` lock twice with a gap in between (the plan job's S26 check, then the android job's install), so a lease taken in that gap is not wrong — it simply makes that run's android job wait on the lock (up to its 20-minute limit) and fail if the lease outlasts it; an `s24` lease never touches a deploy at all. `lease` and `run` connect the phone through the same `findPhone` the deploys use (adb server on 5037, matched by `ro.serialno`, the mDNS nudge included, over Wireless debugging or USB) and give you `ANDROID_SERIAL`, `ANDROID_ADB_SERVER_PORT` and `HUB_DEVICE`; SIGINT or SIGTERM while they look for it stops at once and holds nothing. A phone that does not come within `--wait` (default 2m) prints exactly `HUB_DEVICE_AWAY <device>` on stdout and exits 75, holding nothing, with the reason on stderr (`absent` — turn Wireless debugging on, `unauthorized` — pair again, `offline`); a lock that is not free within `--wait` prints `HUB_DEVICE_BUSY <device> ...` (naming the holder) on stderr and exits 76. Check `$?` for both: never `eval` the output unchecked, or the AWAY line runs as a command. `status` only looks: it never kills, starts or reconnects anything but the emulator pool's own expired leases (below), which every invocation reaps first. `tools/catchup/units/install.sh` installs `~/.local/bin/hub-device`, a wrapper that runs the release's copy.

**Dedicated QA phones.** A phone the owner donates to the hub as a QA device is declared once, privately, in `~/.config/mobile-deploy-hub/qa-devices.json` (or `$HUB_QA_DEVICES`; mode 0600, never committed): `{"schema":1,"devices":[{"name":"S24","model":"SM-S928U","serial":"<ro.serialno>","dedicated":true,"allowed_users":[0]}]}`. The name is the `hub-device` word, so the lease on that name is the reservation, and the serial and model must agree with `android_extra` in `devices.json`; the deploy phone can never be declared dedicated. The seed marks a phone `dedicated_qa` by serial and reads this file only through its `qaDevices` loader (`loadQaDevices`, `$HUB_QA_DEVICES`), keeping `name`, `model` and `serial` and never `allowed_users`; only `hub-device lease|run --match` reads it, to keep a dedicated phone out of a query that does not name it (no other command, and not `status`, opens it; local status shows every value, a service caller passes `dedicatedQaIds(...)` as `qa_ids`), and `hermetic()` points the loader at an empty temp file. An app's QA tooling that drives only its own app on an allowed user may then skip owner-profile isolation (green-in-between: `native/tools/qa/qa_devices.py`). Only one adb server can own a phone's USB interface, so a tool attaches to the server that already owns it rather than starting a second one; a hub-owned server for dedicated phones, taken under the lease, is the open follow-up.

`phone` in place of a device name takes whichever phone is free and reachable: the S24 first, then the S26. It holds a place in line (Story 5.8): one Pool request (`lock.mjs` `acquirePool`) that writes the identical Lease ticket into the queue of every phone, so it stands at the same place on both and no later taker jumps it, and takes the first phone that serves it (the S24 on a tie). The winner takes its phone and withdraws the other ticket (no event, no `cancel` of its own); a request that waits prints one `HUB_LOCK_WAIT phone held by <holder> position=<n> eta=<lo>-<hi>` line on stderr for the held phone with the fewest waiters ahead, the ETA being the earliest of the two phones' (`eta.mjs` `earliest`). A phone that is taken but does not appear is given back (an `acquire` and a `release` in the log, as before) and the request keeps its place on every phone, so a phone that frees or appears mid-wait is still picked up; each phone is given a slice of what is left (`HUB_DEVICE_PHONE_SLICE_MS`, default 10s) to appear. `HUB_DEVICE` in the exports (and the `device` field of `--json`) says which one it took, and `release <id>` of a waiting request cancels it on every phone: the live waiting request writes its one Pool-level `cancel` (`released`) in the log and exits 1 `HUB_DEVICE_CANCELLED`; releasing a killed request's stale tickets writes no event, and its `request` stays without an ending. A request whose process is killed has tickets that read stale by its pid; an acquirer prunes only the queue of the lock it takes, so each ticket goes when that phone's next acquirer prunes it. `--wait 0` is a try: it writes no ticket and takes a free phone only when nobody waits ahead. When no phone comes: every phone held is BUSY (76, naming each holder), a free phone that never appeared is AWAY (75, naming each reason). A single-device waiter queued before the request is served first when its lock frees; the request keeps waiting for the other.

**Ask for a phone by Capability.** `hub-device lease|run --match <query>` takes a phone by what it is instead of by name. The query is comma-separated clauses `key=value`, `key>=n` or `key<=n` (`kind=phone,api_level>=34`; a key is lowercase letters, digits and `_`, and `>=`/`<=` take a number). A clause reads one facet of a Resource: `id`, `name`, `kind`, `host`, `model`, `deploy_target`, then any Capability the Registry records (an intrinsic facet wins a name clash); `=` compares by the facet's type (`true|false` for a flag, a number for a number, exact text otherwise), `>=`/`<=` read only a number, and a Resource without the facet never matches. The matcher is one pure function, `tools/registry/match.mjs` (`parseQuery`, `match(registry, request, policy)`), which the Claims library (`claims.matchTarget`) runs against the in-memory seed and `take` then tries in order as one Pool request named `match:<query>` (the same `HUB_DEVICE`, exports, events and place in line as `phone`: one `request`, then one `acquire`, `timeout` or `cancel`, with the identical ticket in every match's queue). A dedicated-QA phone is served only to a request that names it (`name=s24`, `id=s24`) or asks for `dedicated_qa` (any `dedicated_qa=` clause), and a deploy phone is dropped when `--for` is over its 60 min cap. The committed seed records no Capabilities yet, so `api_level>=34` answers `HUB_NO_MATCH` until the Registry (Epic 6) sets them; `kind`, `model`, `host`, `name` and `deploy_target` queries work now. A request nothing satisfies fails at once, writing no event and holding nothing: exit 2 and one stderr line `HUB_NO_MATCH match:<query> no Resource matches: <id> <why>; ...` naming why each Resource was left out (members on two hosts are `HUB_POOL_CROSS_HOST`, also 2). Members that read `absent`, `offline` or `unauthorized` over the same read-only wire query `status` uses (on the Linux host only; `unknown` never drops one) are dropped before the try, and when every member is gone it prints `HUB_DEVICE_AWAY match:<query>` and exits 75, again with no event. `--match` takes no device word (`lease s24 --match ...` is exit 2), is refused by every command but `lease` and `run`, and its `--for`, `--why`, `--wait`, `--pid` and `--id` are checked before the query is read. The `phone` word's members come from the same matcher, and for the committed `devices.json` are still the S24, then the S26. A take of a Resource `registry.json` marks retired or seed-missing (by its name, or as the last `phone` member left) fails at once with exit 2 and `HUB_RESOURCE_RETIRED <word> ...` on stderr, holding nothing (a `--match` query leaves it out and says `is retired`); holds and queued waiters are unaffected.

```sh
vars="$(hub-device lease s24|s26|phone --for 30m --why 'tower: S24 proof' [--wait 5m] [--holder WHO] [--env-serial MY_DEVICE] [--verbose])" && eval "$vars"
                                                      # exports HUB_LEASE_ID, HUB_DEVICE (s24|s26), ANDROID_SERIAL, ANDROID_ADB_SERVER_PORT; $? is 75 (away) or 76 (busy) otherwise
hub-device release [<lease_id>|--any]                # no id: $HUB_LEASE_ID (what lease exported); a bare release with neither refuses (exit 2) rather than freeing whatever is there; --any frees whichever phone lease is held; a deploy's lock is never touched
hub-device reservation release --run <owner--repo--run> [--name adb|mac-ios] [--json]   # a deploy run's Reservation on this host (announce runs it over ssh on the Mac); exits 0 whether or not one was held
hub-device status [--json]                            # phones (held/free and reachable), leases, every waiter with its position and live ETA, Reservations, and adb servers / emulators / Xvfb displays marked managed or foreign
hub-device discover [--json]                          # read only: the devices this host can see that no Resource names, each with serial, model and adb id (see below)
hub-device run s24|s26|phone [--for 1h --why TEXT --wait 5m --holder WHO] [--env-serial NAME]... [--verbose] -- <cmd...>   # lease, run, release on any exit; returns the command's code
hub-device lease --match 'kind=phone,api_level>=34' --for 30m --why 'who: why'   # a phone by Capability (also `run --match ... -- <cmd...>`); exit 2 HUB_NO_MATCH, 75 every match away
hub-device lease s26 --for 1h --why 'who: why' --no-connect --id my-hold   # the lock only, phone away or not (adapters, e.g. green-in-between's loop-ship hold); the S26 is a deploy target, so --for is at most 60m (use s24 or an emulator for longer)
```

The phones are found the same way over Wireless debugging (the default; the mDNS nudge connects when auto-connect is slow) and over USB (plug in a data cable). `--holder` names who holds the lease (default `$HUB_DEVICE_HOLDER`, else `user@host`); `--verbose` adds the full why-the-phone-was-away detail to an AWAY. `release` answers `HUB_DEVICE_RELEASED` (naming the phone), `HUB_DEVICE_CANCELLED` (it was still queued) or `HUB_DEVICE_NOT_HELD` (nothing, or something else, holds it; exit 0 either way), and exits 1 only when it would have to touch a deploy job's lock or a lock that is mid-change. A `job:<repo>#<run>.<attempt>/<job>` id (a deploy job's place in line, shown by `status`) is not a lease: `release` exits 2 with one stderr line, `HUB_DEVICE_JOB_ID <id> is a deploy job's place in line, not a lease; cancel run <run> of <repo> instead (gh run cancel <run> --repo <repo>)`, and touches nothing (a local run's id, `job:local#local-<pid>.<attempt>/<job>`, says `it is the local process <pid>, stop that process instead`). `status`'s PHONES block asks the hub's adb server over its wire protocol (`host:version`, then `host:devices-l`, plus one `ro.serialno` read for each bare `host:port` id in `device` state, to tie it back to its phone; never the adb binary, `start-server`, `connect` or mDNS), bounded at 5 s and only when the inventory shows the adb server already running, so status still starts nothing — and says for each phone `reachable`, `unauthorized`, `offline`, `absent`, or why it could not ask. `status --json` is one builder (`claims.statusView`) that also walks the free `res-<slug>` and `emulator-<n>` queues, and gives every row of `phones`, `locks`, `waiters`, `reservations` and `emulators` a `resource` (the Resource the lock belongs to, null for a lock that is none, such as `s3-*`), a `deploy_target` and a `reachability` `{state, checked_at, age_ms, stale}` beside the unchanged `presence`. `deploy_target` says whether deploys install to that Resource: true for `s26` and `ios-lane`, false for `s24`, the emulator Pool and any `res-<slug>`, null when `resource` is null. It comes from the Registry seed (`tools/registry/seed.mjs`), which derives every Resource from the committed `devices.json` in memory; `lock.mjs`'s `DEPLOY_TARGETS` and `SEED_RESOURCES` stay as pure name maps, and `seed.test.mjs` keeps them equal to the seed. `state` is one of `reachable`, `unauthorized`, `offline`, `absent`, `unknown`; `unknown` means nobody checked, or the transport could not say, and is never shown as `reachable`. A reading is taken only on the host that owns the Resource (the Linux host reads the phones, the Mac the iPad through `devicectl`, and only when a row names `ios-lane`); every other row, and every row on a host that does not know its key (`HUB_HOST_UNKNOWN`), shows `{unknown, null, null, stale: true}`. `age_ms` is computed on the reader's clock, and `stale` is true when there is no reading or it is older than `registry.reachability_max_age_s` in `tools/ci/policy.json` (60); it is derived, never stored. Its WAITERS block lists every waiter on every walked lock in line order: a Lease as `<device> #<n>  <lease_id>  holder=<h>  why="<w>"  waiting since <t>`, a deploy job as `<device> #<n>  JOB <repo> run <run> job <job>  waiting since <t>` (the catch-up as `CATCH-UP`), each with `eta=<formatEta>` while live (`eta=?` when the ETA could not be computed) and `[stale]`, with no ETA, for a dead ticket. The `#<n>` of a waiter row is its order among the lock's ticket waiters, stale ones included; Reservations are listed apart, each with its `place` in the whole line. The wait line's `position=<n>` counts the blocking entries ahead plus one, so the two numbers differ when a stale ticket or a blocking Reservation stands ahead. A Pool request (`phone`, `--match`) waits in every member's queue but is listed once, with the keys of the member where it stands nearest the front, its `eta` the earliest of the members', and `  pool <pool> (<lock> #<n>, ...)` appended in text (`--json` adds `request`, `pool` and `positions: {<lock>: n}` to that row alone); a DEPLOY TARGET line counts it for every deploy target it waits on. Between WAITERS and RESERVATIONS, one `DEPLOY TARGET <resource> (lock <lock>)  <held|free>  <n> waiting[  <r> reserved]  deploys install here; a lease on it holds deploys back` line appears for each deploy target that is held, waited on or reserved (nothing is printed otherwise). A RESERVATIONS block follows, only when a Reservation exists: `<device> (<lock>)  <run_key>  place <n>  grace <pending|running until <iso>|over>  expires in <age> (<iso>)`, marked `[blocking]` or `[expired]`. `--json` keeps every key and adds `waiters[].kind/repo/run/job/eta` (`{lo_ms, hi_ms, low_data}` or null) and a top-level `reservations[]` (`lock, device, run_key, repo, run, place, blocking, grace, reserved_at, expires_at, stale`). `status` stays read-only: it reads the Event Log once, in the policy window, and writes nothing (it starts no grace and prunes nothing).

`hub-device discover [--json]` lists what the host can see that no Resource names (FR-4). On the Linux host it asks the hub's adb server on `HUB_ADB_SERVER_PORT` (default 5037) with the same read-only wire query `status` uses (`reachability.queryAdb`: `host:version`, `host:devices-l`, one `ro.serialno` read per bare `host:port` id in `device` state, bounded at 5 s), only when the inventory shows that server already running; it never starts a server, connects or runs the adb binary, and writes nothing to the lock dir or the Event Log. It prints every listed device that no phone Resource of the committed `devices.json` names (by serial, mDNS id or the serial read from a `host:port` id), skipping `emulator-<n>`, as `<serial>  <model>  id <id>  <state>` under a header that names the port used; `--json` is `{format: 1, port, devices: [{serial, model, id, state}], host, via, note}`. With no adb server it says `no adb server (nothing was started)` and exits 0; a server that does not answer (`note: adb did not answer`) prints and exits 1. On the Mac it lists the `devicectl list devices` records whose UDID `devices.json` does not name (`via: devicectl`, `port: null`; `devicectl did not answer` exits 1) and lists no Android device, because the Mac's adb is not the hub's. The host key picks the transport, so a host without one fails (`HUB_HOST_UNKNOWN`, exit 1). The QA file is never read.

The hub's own adb server (the port deploys use) is `managed`; an emulator or Xvfb is `managed` only when its environment has `HUB_MANAGED=1` or its pid is in `<lock dir>/managed.json` (`{"pids": [...]}`), and everything else is `foreign`.

Rollout: leases are honoured only by hub code with this `lock.mjs`. A deploy on an older pin (`actions/hub@v1.2.25` and before) and a catch-up from an older `current` see a lease's short-lived `pid` as a dead job and reclaim the lock at once. So the hub release that carries leases (the pin flip) must land before, or with, `hosts:install` putting `hub-device` on PATH; until then `lease` and `run` print one warning on stderr when `~/.local/share/mobile-deploy-hub/current` predates leases — that warning sees only the installed catch-up, never the deploys' pin, so the pin flip landing first is the only real guard.

### Emulators

`hub-device lease|run emulator` gives you a throwaway emulator from a small pool instead of the phone: made for your lease and torn down at its end. Nothing about it is shared, so it never touches anybody else's emulator, adb server or AVD.

```sh
vars="$(hub-device lease emulator [--profile default|playstore] --for 30m --why 'tower: layout proof' [--wait 5m] [--id ID] [--pid N] [--holder WHO] [--env-serial MY_DEVICE] [--json])" && eval "$vars"
                                                      # exports HUB_LEASE_ID, ANDROID_SERIAL (emulator-<port>), ANDROID_ADB_SERVER_PORT; $? is 76 when the pool is full
adb shell getprop ro.kernel.qemu                      # the exports point adb at the emulator's own server
hub-device release emulator [<lease_id>]              # no id: $HUB_LEASE_ID; an empty or malformed id is refused (exit 2), never "any lease"; `hub-device release <lease_id>` works too
hub-device run emulator [--profile default|playstore --for 1h --why TEXT --wait 5m] [--env-serial NAME]... -- <cmd...>   # make, run, tear down on any exit; returns the command's code
```

- **What a lease makes.** A private adb server on a free port in 15000-15099 (never 5037; it never scans the shared emulator ports 5555-5585 and never connects over mDNS or USB (`ADB_MDNS=0`, `ADB_USB=0`), so it cannot pick up the S26 or somebody's emulator), a free even console port in 5600-5698 whose adb port (+1) is free too and overlaps nobody's pair (5554 never; a `HUB_EMULATOR_CONSOLE_PORTS` override reaching below 5586 is refused), and its own AVD `hub-<lease_id>` made by `avdmanager` from the profile in its own AVD home under `~/.cache/mobile-deploy-hub/emulators/<lease_id>/` (never `~/.android/avd`). The emulator starts headless (`-no-window -no-audio -gpu swangle_indirect -no-snapshot -wipe-data`) with its own `TMPDIR` and `XDG_RUNTIME_DIR`, so it never shares a netsimd or discovery file, and the lease returns once `sys.boot_completed=1` (`HUB_EMULATOR_BOOT_TIMEOUT_MS`, default 6 min). `--for` runs from that moment, so a slow boot never eats the lease.
- **Profiles.** Both are API 36, x86_64, 1080x2400 at 420 dpi, 2 GB, 4 cores. `default` uses `system-images;android-36;google_apis;x86_64` and `playstore` uses `system-images;android-36;google_apis_playstore;x86_64`. Each uses exactly its own image: no fallback, no download. A missing image fails at once with one line naming it and the `sdkmanager` command that installs it. Both are installed on big-chungus.
- **The record.** `<lock dir>/emulators/<lease_id>.json` and the slot's lease record name every process the lease started (adb server, emulator, and the helpers it daemonizes, such as crashpad_handler and netsimd, found by the lease's own `HUB_EMULATOR_LEASE=<lease_id>.<nonce>` environment marker, the nonce kept in the record), each with its process start time, plus every path it made. Release or expiry signals exactly those processes, each only after checking its pid still has the recorded start time: SIGTERM, then SIGKILL after `HUB_EMULATOR_KILL_GRACE_MS` (default 15s), the emulator and its helpers before its adb server. It then rescans for the lease's marker and stops, the same way, any helper started during shutdown. Then it deletes the AVD (`.ini` and `.avd`), the folders and the record, and frees the slot and the ports. Nothing is ever killed by name, pattern or process group. If any recorded or marked process will not die, the record stays, so its slot stays out of the pool until the next reap succeeds. A release frees the slot lock before the teardown, so a `lease` still booting that emulator ends as `HUB_DEVICE_CANCELLED emulator`. The record keeps the slot out of the pool until the teardown is done.
- **The cap.** At most 2 emulators at once. The cap is the host's: `$HUB_EMULATOR_POOL`, else the number in `<lock dir>/emulator-pool`, 1 to 8. A request may pass `--pool N` only to ask for fewer, and a larger N is refused (exit 2). Slots are the locks `emulator-1` .. `emulator-N`. Requests queue first in, first out on the `emulator` lock: the first in line holds it and takes the first slot that frees. `--wait` (default 2m) bounds the wait, and a full pool exits 76 with `HUB_DEVICE_BUSY emulator the emulator pool is full ...` on stderr, naming the slots' holders, or the requests ahead when others are already waiting. `release <id>` cancels a request that is still waiting.
- **The reaper.** There is no timer, cron job, unit or Candybar job. Every `hub-device` invocation (`status` included) first tears down the pool's leases that expired, whose `--pid` holder (or `run` process) is gone, or whose slot no longer holds them. It touches only their recorded, identity-checked processes and logs `HUB_EMULATOR_REAPED <id> <slot> (<why>)` on stderr. So an expired lease keeps its emulator until the next `hub-device` call on the host. While a lease is still being made it is tied to the process making it, so killing that process mid-boot leaves nothing for long.
- `status` lists the pool's emulators under EMULATORS, and in the inventory their adb server and emulator are `managed (lease <id>)`. Everything else stays `foreign` and is never touched. Linux (big-chungus) only. Prefix `heavy` (`heavy hub-device run emulator -- ...`) to put the boot in `batch.slice`.

## The App Store listing

A store page is data, not clicking. Each app keeps `store/apple/listing.json` in its own repo, and the hub reads and writes it through the App Store Connect API:

```bash
mise run listing pull ~/code/tolt/tower-of-lost-things                 # snapshot the ASC listing into store/apple/listing.json
mise run listing push ~/code/tolt/tower-of-lost-things                 # print a field-by-field diff, write nothing
mise run listing push ~/code/tolt/tower-of-lost-things --apply true    # write it, read it back, fail if anything differs
```

The app is found from the hub policy: the checkout's `owner/name` (its git remote, or `--repo`) names an `apps` entry, and that entry's `ios.store_bundle` (else `ios.bundle`) is the App Store bundle id. Keys come from 1Password at call time: the App Manager key by default, and the Admin key for the writes Apple keeps to Admin (content rights, price, availability), which the tool switches to by itself. `HUB_ASC_KEY=admin` runs everything as Admin. No value is written anywhere.

`listing.json` covers: app name, subtitle, privacy policy URL; promotional text, description, keywords, what's new, support and marketing URL; copyright; primary and secondary category with subcategories; content rights; price and availability; every age rating question (the file must answer all of them, Kids age band included); App Review contact, notes and demo account; and an `exportCompliance` check. A field the file leaves out is not managed. A value of `op://...` is read from 1Password at push time (review phone number), and `pull` keeps such references instead of writing the value; `pull` never writes review contact fields. `schema`, `locale` and the field names are checked strictly, with Apple's length limits, so a bad file fails before any call.

**Price and availability** are two more optional groups, written whole and only when the file has them:

```json
"price": { "baseTerritory": "USA", "customerPrice": "0.00" },
"availability": { "territories": ["USA", "CAN", "AUS", "NZL"], "availableInNewTerritories": false }
```

`customerPrice` is the base territory's price as text (`"0.00"` is Free); the tool looks up Apple's price point for it, and Apple works out the other territories. `territories` is every country the app is on sale in (three-letter codes, and the base territory must be one of them); `availableInNewTerritories: false` keeps it out of countries Apple opens later. Apple lets only the **Admin** key read or write these, so the tool switches to it by itself for these calls and only when the file has the groups; a diff or push of a file without them never uses the Admin key. A first push writes the whole record; later, a change to the territory list flips just the territories that differ and a price change writes a new price schedule. Apple's API cannot change `availableInNewTerritories` once an app has availability, so the tool stops with a message and that one switch is changed in App Store Connect (Pricing and Availability). Both are read back after a push and must match. `pull` reads them only for a file that already has them.

Screenshots are PNGs under `store/apple/screenshots/<DISPLAY_TYPE>/NN-name.png` (`APP_IPHONE_67` takes 1290x2796 or 1320x2868, `APP_IPAD_PRO_3GEN_129` takes 2048x2732 or 2064x2752), kept out of git and made by the app's own script. A push compares file checksums and order with what Apple holds, and replaces a whole set only when it differs, so a second push writes nothing. `--only screenshots` pushes just the screenshot sets and leaves every text field as App Store Connect has it (use it when someone edited the copy there and the file has not caught up; `pull` brings that copy home); `--only fields` is the reverse. A screenshot that was uploaded with the Admin key can only be deleted with it, so a delete the App Manager key is refused is retried once as Admin.

It never touches builds, TestFlight groups, in-app purchases or review submission. `exportCompliance` is only compared with the latest build's `usesNonExemptEncryption` and reported. App Privacy (the nutrition label) has no public API; keep the exact answers beside the listing as `store/apple/app-privacy.md`.

## Hosts and checks

For the iOS job's ephemeral token boundary and the authorized new TestFlight
**dry-run + rerun** procedure, see [iOS history transport proof](docs/ios-history-transport.md).
That diagnostic proves authenticated history access only, not upload eligibility.

```sh
mise run check          # actionlint on the workflow, then node --test 'tools/**/*.test.mjs' (the catch-up included)
mise run --tool node@26 check   # the same task on Node 26 (the task pins 24); check.yml runs both legs on every push
mise run conformance    # every app still deploys only through the hub (gh api); every deploy's gate runs it on its own checkout too
mise run hosts:install  # the bucket index, hub-mac, each host's key (~/.config/mobile-deploy-hub/host-key), the Mac's quickdrop .stignore and handoff cache, the catch-up units and the Mac watchdog
```

The catch-up installs only on a host in live mode, and both are live since 2026-10-09 (`catchup.mjs mode` prints it; every gate logs `HUB_CATCHUP_MODE`, and a pending device on a host in watch mode reads "catch-up off" in the event and on the page):

```sh
node ~/.local/share/mobile-deploy-hub/current/tools/catchup/catchup.mjs mode live          # big-chungus
ssh hub-mac '~/.local/share/mise/installs/node/24/bin/node ~/.local/share/mobile-deploy-hub/current/tools/catchup/catchup.mjs mode live'
```

The Mac watchdog (`tools/ci/macwatch.mjs`, fired every 2 minutes on big-chungus by the candybar `mobile-deploy-hub-macwatch`, which runs its `.service`; there is no timer) cancels a deploy run whose Mac job has waited longer than `mac.queue_limit_min` for its runner, once the run's APK half is done; it uses big-chungus's `gh` login. `HUB_MACWATCH_*` lines in its journal say what it did.
