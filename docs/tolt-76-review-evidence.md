# TOLT-76 strict Store retry and release review evidence

This branch is a review candidate, not a hub release. No version was bumped, tag moved, application uploaded, or device installed by these checks.

## Reproduced blockers and guardrails

- The old Tower upload path selected a new build from the current ASC list inside `upload`, after Linux had already exported a build. If assignment failed after a successful upload, a retry could restamp the old receipt and upload another build. Tower now uses the exported version/build as immutable identity. The hub queries `ios.store.state` before calling upload, and an exact present build skips upload and retries assignment. Tower refuses build-selection drift and records an exclusive durable upload attempt before invoking native upload, so an Apple-accepted upload not yet visible in ASC cannot be repeated on that Mac. A previously attempted but still invisible build requires reconciliation rather than a second upload.
- Strict Store delivery refuses missing `ios.store.preflight` or `ios.store.state` at the gate, before `plan` spends a version. Tower's Mac preflight checks ASC access, the Owner Testing group, pinned Xcode/SDK, profile identity/expiry, and the distribution signer; the hub also probes signing and declared secrets. A strict assignment is marked `assigned` only after the hook prints an exact-build/group receipt; Tower prints it only after ASC confirms group membership. Tester invitations are reported separately and cannot be inferred from assignment.
- Dry device targets need a verified built artifact with SHA-256 and build before they become `checked`. A TestFlight dry check requires the verified signed Store IPA and successful state query; an unhanded Xcode project is `skipped`. A mere `dry run` message is not evidence. Independent re-review found that Tower's Linux-export handoff has no `ios.store.build`: its private IPA and store Xcode tarball do not supply a signed Store IPA. The normal Tower native upload creates the Store IPA only while actually uploading, so a no-upload dry run cannot claim Store signing proof. The hub now records that dry target as `skipped` (no `proof`) after the state query, leaving the release gate **on hold** until the app's normal Mac dry handoff can build and inspect an exact-build Store IPA or equivalent native preflight evidence without uploading. No private IPA was reused as a Store IPA.
- Independent re-review also reproduced a Tower `COMPLETE` completion artifact listing only `S26` and `iPad`, which the earlier release validator accepted. `release.mjs` now derives device targets from each policy app's lanes and also requires `TestFlight` for every policy iOS lane under the strict Store completion rule; Android-only apps remain Android-only. This check cannot be bypassed by omitting TestFlight from the artifact's own `required` list.
- `release.mjs` downloads `completion-out` for each watched run and requires the same repo and run, `COMPLETE`, dry and unbumped, all required targets checked, and no owed targets. Missing, unreadable, or incomplete evidence follows the red rollback path, not the successful workflow-exit path.

## What remains

Independent spec and quality re-review of the pushed hub candidate remains required. **Hold release:** Tower's Linux-export path cannot yet prove the signed Store IPA without performing its native upload; a safe, real Mac dry-handoff Store build/preflight seam must be implemented and independently verified before release. Separately, the live main manifests for Green In Between, Gruvato, and Navi lack the `ios.store.preflight`/`ios.store.state` hooks the strict gate now requires; their owners must integrate those hooks in their app repos. Do not bypass policy per app, edit those repos here, or start the six-app release dry runs until these prerequisites are met. After review/approval and prerequisite integration, the operator must recheck refs, land the reviewed hub source on main, select an unused hub patch version, and run the normal `mise run release -- X.Y.Z` from clean origin/main. Release approval, any actual application shipment, and tester availability remain separate; build 10's betaGroup 403 cannot prove testers can install. No release, application bump, upload, or device install is authorized by this evidence.
